Case study

ControllerPlayground

A controller-first Windows gaming shell, built for the couch, with C#, WinUI 3 and a native C++ input layer.

  • C#
  • .NET 8
  • WinUI 3
  • C++
  • Microsoft GameInput
  • SteamKit2
  • Steam Web API
  • XAML
View code on GitHub

The problem

A PC is a great gaming machine, but Windows still assumes a desk, a mouse and a keyboard. Plug a PC into a TV and pick up a controller, and you quickly hit screens you can't navigate, text boxes you can't type in, and launchers that each work differently.

ControllerPlayground explores what a Windows gaming interface looks like when it's designed for a controller first: console-style navigation, a game library, friends and chat, and overlays, all reachable without touching a mouse.

Architecture

The app is split into layers so each one has a single job. Raw controller input is captured in native code, normalized per device in C#, and routed by the shell to whichever screen or overlay currently owns input. The on-screen keyboard runs as its own process and talks to the shell over a local pipe.

Hard problems I solved

1. A stable boundary between C++ and C#

I chose Microsoft GameInput mainly for its DualSense support. It's a C++ API, so I wrote a small native DLL over it and call that from C#. The risk with native interop is that both sides must agree on memory layout exactly, or you get corrupted input with no error.

Every struct that crosses the boundary uses fixed 8-byte packing, and the C++ side static_asserts each size (for example, a device snapshot is exactly 144 bytes), so a layout mistake fails the build instead of failing at runtime. When I added multi-controller support, I added a v2 API alongside the original one rather than changing it, so existing callers kept working.

2. Two controllers, one interface

With an Xbox controller and a DualSense connected at once, the question becomes: who is in charge? If player two can press a button inside player one's menu, the UI breaks in confusing ways.

Each device gets a full identity from GameInput instead of a guess from vendor and product IDs. Either controller can navigate the home screen, but whoever opens a menu owns it, and input from the other controller is discarded rather than queued for later. Sticks and buttons have to return to neutral before a different controller can take over, which prevents a held button from "leaking" into the next screen. Disconnecting a controller revokes its ownership.

3. An on-screen keyboard in its own process

Typing with a controller needs an on-screen keyboard, and I wanted it isolated from the main shell. That means the two processes have to coordinate input safely across a process boundary.

The keyboard and shell talk over a local named pipe with a versioned protocol. The shell checks the connecting process before trusting it, every message has a size limit, and each keyboard action must be authorized by the shell with a short-lived, one-time ticket. Stale or duplicate commands are rejected instead of retried, and the keyboard always types for the controller that opened it.

4. Real Steam integration

The shell signs in to Steam by QR code through SteamKit2 and stores the refresh token in the Windows Password Vault, so users don't sign in every launch. It reconnects automatically, loads friends and chat, and finds the local Steam install through the registry to parse Steam's own VDF config files. Game pages pull news from the Steam Web API.

How I verify it

  • 109 automated test groups pass in both Debug and Release builds
  • 28 protocol and session test groups also pass with JSON reflection disabled
  • End-to-end hardware checks with Xbox and DualSense controllers across home, library, game pages, Guide, friends, chat and the keyboard, including launching and returning from a real game

Each milestone has a written acceptance record in the repo that lists exactly what was tested and what wasn't.

Known limitations

  • Steam Input's Desktop Layout can inject its own keyboard and mouse events alongside GameInput; it has to be disabled for now.
  • Windows packaging, installation and upgrades haven't been validated yet.
  • Only x64 is supported, and Steam Controller support is planned for a later milestone.
